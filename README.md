# Согласование актов скрытых работ — бета (кликабельный прототип)

Фронтенд на React + Vite + TypeScript + Ant Design. Работает в двух режимах:

| Режим | Сборка | Данные |
|---|---|---|
| **Демо** (GitHub Pages) | `npm run build` → `dist/` | в браузере: состояние в localStorage, PDF в IndexedDB; у каждого тестировщика своя копия, есть панель «ДЕМО» (сдвиг времени, сброс) |
| **Сервер** | `npm run build:api` → `dist-api/` | общая база PostgreSQL через NestJS API ([`backend/`](backend/README.md)); логика и права — на сервере, данные обновляются каждые 15 с и при возврате на вкладку |

Интерфейс в обоих режимах один и тот же. Переменные сборки: `VITE_API=1` — серверный режим (задаётся файлом `.env.api`),
`VITE_API_URL` — адрес API, если он не на том же домене (по умолчанию `/api`), `VITE_DEMO_LOGINS=0` — скрыть кнопки быстрого входа.

## Локальное тестирование
См. **[LOCAL-TEST.md](LOCAL-TEST.md)**: демо-файл без установки, стенд в Docker (`start-local.sh` / `start-local.bat`, http://localhost:8080) и сценарий проверки по ролям.

## Запуск
```bash
npm i
npm run dev              # разработка, http://localhost:5173
npm run build && npm run preview   # сборка, http://localhost:4173
npm run build:single               # один файл dist-single/index.html (открывается двойным кликом)
npm run dev:api                    # серверный режим, /api проксируется на localhost:3000
npm run build:api                  # серверный режим → dist-api (его раздаёт backend)
```

## Тестовые объекты
По умолчанию база **пустая**: есть пользователи и справочники, объектов нет. Тестовые объекты создаются только по запросу — `SEED_DEMO_OBJECTS=1 npx tsx prisma/seed.ts`, `start-local --demo`; они же используются автотестами.

1. №1 Тверская: пустое выполнение, можно пройти весь цикл с нуля. Если один подрядчик подаст весь объём (например, 1.1 — 3000 пог. м и 1.5 — 1800 пог. м), второму уйдёт форма с нулями (подаётся автоматически).
2. №2 Ленинградский: «Механика-Дор» подала форму, у ИП Соколов черновик, недостача 96 м².
3. №3 Садовое: обе формы у заказчика на проверке.
4. №4 Варшавское: заказчик одобрил обе формы, акт на проверке у ГП.
5. №5 Профсоюзная: выполнение 1 согласовано (можно выгрузить Word и отправить в архив), в выполнении 2 заказчик отклонил форму ИП Соколов.
6. №6 Кутузовский: в архиве, три подрядчика.
7. №7 Дмитровское: «Механика-Дор» подала весь объём, у «ТермоЛинии» и ИП Соколов автоматически поданы нулевые формы, акт у заказчика (client2).
8. №8 Большая Никитская: после одобрения заказчиком изменён титул 250 → 280 м², формы возвращены на пересчёт.
9. №9 Новослободская: пустое выполнение, три подрядчика.

## Объекты и выполнения
- Создавать, изменять и удалять объекты и выполнения могут только **ГП** и **заказчик** (заказчик — только свои объекты). Менеджер и подрядчики этого не могут.
- У объекта есть **общий объём**, у выполнения — свой объём. Сумма объёмов выполнений не может превышать объём объекта. Объём объекта нельзя сделать меньше уже распределённого.
- Удалить объект или выполнение можно, пока по ним нет согласованных или архивных актов. Вместе с ними удаляются формы, акты и чат. Участники получают уведомление.
- Формы в модальных окнах при закрытии (клик мимо окна, Esc, «Отмена») спрашивают подтверждение, если введены данные.

## Уведомления
- Типы: «Требует действия», «Важное», «Напоминание», «Инфо».
- Группировка по объектам, дням или типу. Группы с непрочитанными «требует действия» показываются первыми.
- Фильтры: тип, период, поиск, только непрочитанные. Можно отметить прочитанной группу или все показанные.
- Напоминания для ГП и менеджера приходят одной сводкой за проверку, а не отдельным сообщением по каждому выполнению.

## Блок «Требует внимания» (дашборд)
Только важные события: изменение объёма выполнения, отклонение формы заказчиком, возврат ГП, отзыв уже одобренной формы. Выполнения «без движения» сюда не попадают, по ним приходят напоминания.

## Логика согласования
Подрядчики → (сумма = титул) → **заказчик** (решение по каждой форме) → **ГП** (акт целиком) → Word → архив.

- У выполнения один **общий титул в м²**. Подрядчик сам добавляет в форму виды разметки и вводит погонные метры, система переводит их в м². Сумма м² всех подрядчиков должна совпасть с титулом.
- **Перебор** над титулом блокирует подачу. **Недостача** ставит форму в статус «Ожидание партнёра».
- Когда сумма объёмов равна титулу, подрядчики, не подавшие форму, **автоматически отправляют форму с нулями** (без файлов). Если такой подрядчик выполнял работы, он отзывает нулевую форму и подаёт свою. Если форму отзывает тот, кто выбрал весь объём, нулевые формы тоже сбрасываются.
- Когда сумма сошлась, создаётся акт и уходит **заказчику**. Заказчик одобряет или отклоняет каждую форму. Если отклонена хотя бы одна форма, акт уходит на доработку. Одобренные формы остальных подрядчиков сохраняют одобрение.
- Когда все формы одобрены заказчиком, акт уходит **ГП**. ГП согласует его или возвращает на доработку формы выбранных подрядчиков. Комментарий ГП заказчик не видит. Возвращённые формы после исправления снова проходят заказчика.
- **Изменение титула в ходе согласования** (п. 7): ГП обязан указать причину. Все поданные формы, включая одобренные заказчиком, переходят в статус «Изменён титул — нужен пересчёт», акт уходит на доработку, одобрения снимаются. Событие выделяется в журнале выполнения и в истории акта, на выполнении появляется баннер «было → стало», а в дашборде — пункт в блоке «Требует внимания». Подрядчики, заказчик и ГП получают уведомления. После согласования ГП менять титул нельзя, для правок есть «Корректировка».
- Кнопка **Word** выгружает пустой .docx. Позже сюда подключится шаблон бланка.
- Кнопка **«В архив»** есть в карточке акта, в карточке выполнения и в шапке объекта (архивирует все согласованные акты объекта).
- Отозвать форму можно, пока акт не ушёл к ГП.
- Корректировка после согласования доступна только ГП, с обязательной причиной.

## Backend

В папке [`backend/`](backend/README.md): NestJS + Prisma + PostgreSQL — JWT-авторизация, роли, CRUD объектов и выполнений,
вся логика согласования, файлы (local/S3), уведомления, Telegram, напоминания 2/5 дней, e2e-тесты. Запуск — в backend/README, выкладка на сервер — в [`deploy/README.md`](deploy/README.md).

CI (`.github/workflows/ci.yml`) на каждый push: сборка обоих режимов фронтенда, API-тест (43), UI-тест в браузере (17), проверка Docker-образа.
